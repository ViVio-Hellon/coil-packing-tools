# 移植計画 — 既存 python-web-tools への統合

解析結果は [`VBA解析.md`](VBA解析.md)、判断待ちは [`不明点.md`](不明点.md)。

## 1. 既存 python-web-tools の調査結果

`ViVio-Hellon/python-web-tools` VER2.75.0 を調査した。
Flask + 素のESモジュール + SQLite、追加依存は `Flask` と `waitress` の2つだけ。
テスト71本、ゴールデンファイル方式、起動基盤は基盤仕様書どおり。

**守られている約束は今回もそのまま守る**(`docs/設計.md` §1):

1. 業務判断はすべて Python。JS はビューモデル→DOM の純関数だけ
2. API は更新後のビューモデル一式を返す(差分ではない)
3. HTTPステータスで断りの種類を分ける(400 形 / 422 業務 / 403 資格 / 409 競合)
4. 断りの種類は `reason` 定数で運ぶ。文言から推し量らない
5. 同じ事実を2か所に持たない
6. 一覧に無いものは選べない(サーバでも確かめる)
7. 色だけで意味を運ばない。色の出どころは `tokens.css` ただ1つ
8. 移植したアルゴリズムは1行も変えない

### 重要な発見

**既存は `1P1xxx`(板・ザラ板の2次元敷き詰め)、今回は `1C1xxx`(コイル)。**
選定・配置アルゴリズムに重複は無い。重複するのは参照データ源と起動基盤。
したがって既存の `board_selection_algorithm` / `placement_algorithm` は触らない。

**参照パスが一致している。**

| VBA | 既存 python-web-tools |
|---|---|
| `PATH_AIM_参照` | `config.DEFAULT_MASTER_DB_DIR` = `\\nlmfangyshrd\各課共有\0130_日軽稲沢\梱包課\AIM\【■】_参照用ファイル` |
| `PATH_仕掛_参照` | `config.LOT_DB_DIR` = `\\nlmsrvngy03\Read\【New】仕掛\台帳` |

**Access → SQLite は上流で完了済み。**
`source_db.py` に「以前は Access だった。ODBCドライバの有無で動いたり動かなかったり
し、Linux では mdbtools が要った。取り込み元が sqlite3 になったのでその分岐は不要」
と記録がある。`config.py` も `梱包資材マスタ.sqlite3` /
`SIKALOT.sqlite3` / `SIKAHIKI.sqlite3` / `SIKAODR.sqlite3` を見に行く
(`SIKA*NOW` からの改名も `変更履歴.md` に記録あり)。
**cscript.exe → VBScript → ADODB → ACE の経路は不要。**

**ロット検索の辿り方が同じ。**
既存 `lot_service.py` は `SIKALOT → LOTNO で1行 → SIKAHIKI で同じLOTNOの行 →
SIKAODR で同じオーダーNOの行を展開` という順で辿る。
これは VBA の `LOT検索` + `フォーム展開` と同じ道筋。

## 6. 検証

**ゴールデンファイル**(既存 `tests/golden/` と同じ方式)。

- 入力: `(包装仕様No, 板厚, 板幅, 製品単重, 検入数, コイル外径, 梱包単位_重量, 梱包単位_枚数)`
- 期待値: `(パレット種類, パレット名称, パレットサイズ, 積数, 台数, Re_積数, Re_台数,
  最下部長さ, 最下部長さ_短, リプラ長さ, 長い本数, 短い本数, 本数, リプラ計算, HB枚数, 各フラグ)`

**境界値**

- 個別規則15件それぞれの厚み・幅の一致 / 不一致
- 1本不可の `x = 1` と `x ≥ 2`
- 割り切れる検入数 / 割り切れない検入数
- 高さ制限にちょうど当たる積数
- 外径がパレット上下限ちょうど
- 1C1103 の 780 / 800 / 890 / 990
- 1C1258 の 780 / 781 / 1249 / 1250 / 1330

**例外**

- 包装仕様No未登録 / 引当データなし / 収まるパレットが無い
- リプラ長さがリストに無い / 積数0 / 発注票の追記5件超

**帳票**

チェックリスト13項目と発注票のセル内容を、改行を含む文字列で突き合わせる。

現行VBAで実際に処理したロットの入力と計算結果があれば、そのまま期待値にする。
無い場合はコードから導いた値を期待値にし、
**「コード由来であり実績照合前」と明記**して進める。

## 7. 運用

### Access → SQLite

上流で完了済み(§1)。標準ライブラリの `sqlite3` だけで届く。
方言差で効いてくるのは次の3点で、移植時に吸収する。

- **型がゆるい** — Access の数値型が SQLite では TEXT で入っていることがある。
  既存は取り込み時に `to_int` / `to_real` / `to_text` で明示変換しており、同じ作りに乗せる
- **`IsNumeric` の意味** — VBA は `"データなし"` という**文字列**で「指定なし」を
  表現している。Python 側では「値」と「指定なし」を型で分けて持つ
- **文字列フラグ** — `"〇"`(ｺｲﾙ間は間紙入)などはそのまま文字列で比較する

### 複数PC・複数ユーザーの同時書き込み

| 対象 | 置き場所 | 競合の扱い |
|---|---|---|
| 梱包資材マスタ / 仕掛台帳 | 共有フォルダ(読むだけ) | `file:…?mode=ro` で開く。上流が書いている最中でも壊さない。BUSY 10秒待ち |
| 手元の作業DB | 端末ローカル | 取り込んだ写しなので競合しない |
| 発注履歴(共有にする場合) | 共有フォルダ | **ここだけが本当の同時書き込み** |

共有SQLiteへ書くときの方針:

- **WALは共有フォルダでは使えないことがある**(共有メモリを置けない)。
  既存 `enable_wal` は失敗しても既定のまま続ける作りで、そのまま使う
- **`database is locked` はリトライで吸収** — `sqlite_toolkit.execute_with_retry`
- **書き込みは1トランザクション・短時間で閉じる。** 画面を開いている間ずっと
  接続を持たない(既存は「要求ごとに接続を取り直す」規約)
- **追記のみ。** 発注履歴は追記しかしないので行の更新競合が起きない
- それでも共有フォルダ上のSQLiteに書くのは、SMBのロックが当てにならない環境では
  推奨されない。履歴を全端末で共有したい場合は、**端末ごとに書いて定期的に集約する**
  (既存 `outbox_sync.py` と同じ考え方)ほうが安全 → 不明点 Q3 の判断に合わせる

### 長時間放置

既存基盤が扱い済み。**監視レベル1**(入力・計算・帳票のツール)として乗せる。

- **DB接続を持ち続けない** — `sqlite3` の接続はスレッドをまたげないので、
  既存は要求ごとに取り直す規約。ファイルハンドルもロックも残らない
- **古いデータを持ち続けない** — マスタは取り込み時点の写し。
  **日付が変わっても自動では取り込み直さない。** 現行VBA(起動のたびに読む)と
  挙動が変わるので、**画面に取り込み日時を出し、古ければ促す**
- **画面が居なくなったら終わる** — `idle_exit`(心拍20秒 / 途切れて90秒 /
  閉じた合図から8秒)。処理中は落とさない。**開いている間は終わらない** ──
  裏に回った(最小化を含む)画面は心拍が途切れても待ち、PCのスリープ
  明けは待ち直す(2026-09-25 の現場の指摘)
- **ブラウザ放置後の再操作** — 接続断の帯を出して再読込を促す。
  サーバ側の作業状態はプロセスに1つで保存しないため、サーバが落ちていれば消える。
  **15行のチェックリストは SQLite に持たせて残す**(現行の「ブックに残る」に合わせる)

### 上流更新との競合回避

VBA の `TimeDesignation`(毎時59分45秒〜0分45秒を避ける)と
`FileDesignation` / `FileExistence`(`PLEASE WAIT.txt` を待つ)は、
Access ファイルを直接開いていたための作り。
取り込み元が sqlite3 で読み取り専用オープンなら、上流が書いている最中でも
壊さないため、**BUSY待ち + リトライで置き換えられる**。
ただし 2系統パスのフォールバックが今も要るかは確認が要る → 不明点 Q11。
