VBA を読んだだけでは意図を確定できなかった点の一覧。
**いずれも現行の計算結果を変えずに移植している。**
確認のうえ「直す」判断が出たものだけを、設定または個別対応で変更する。

- **A** … 帳票の数値に影響する。現場確認を推奨
- **B** … 挙動に影響するが数値は変わらない

記号ごとに担当のドキュメントが分かれている。

## A-1. 高さ計算の二重化 → **統一（2026.09 / VBA 側で対応）**

**場所**: `SetCoilDimensions`（①）と `GetHBCoilDimensions`（②）

VBA は「コイルの積み高さ」を別々の場所で 2 回計算していて、値が一致しなかった。

```
① TA = 本数×巾/1000 + (本数+1)×0.7/1000
② TA = (本数×巾 + (本数+1)×0.7/1000) / 1000
```

② は **`/10^3` の位置が誤っており、括弧の中で mm と m を足していた**。
結果チップボール分（11本で 8.4mm）が実質消えていた。

### 決定 ― ① が正しい。共通関数へ集約

VBA 側で次へ集約された。移植側も同じ形にした。

| VBA | 移植側 | 内容 |
|---|---|---|
| `GetCoilWidth()` | `SizeMaster`（データ化済み） | 巾。14 分岐を 1 箇所に |
| `GetCoilTA()` | `tare_calc.get_coil_ta()` | 高さ |
| `GetCoilGAI()` | `tare_calc.get_coil_gai()` | 外周 |

`GetHBCoilDimensions` は `GetCoilTA()` を呼ぶだけになり、**① と同一の値**になる。

> **「HB は割れないよう積高より低い」という話は取り下げ**（A-1b）。
> 実測と突き合わせた結果、差が一定でなかった。

### 影響 ― **帳票の数値が変わる**

全 8,400 通り（チップボール 3 種 × 14 サイズ × 4 梱包 × 1〜50 本）で
新旧を計算して比較した。

| | 変わる件数 | 変わり方 |
|---|---|---|
| ハードボードの行 | 8,304 / 8,400 | **最大 +0.096kg**（50本） |
| **風袋** | **456 / 8,400** | **+1kg** |
| **GW** | **456 / 8,400** | **+1kg** |
| 梱包高さ | 0 | 変わらない |

風袋・GW が動くのは丸めの境界にかかる本数。TIP1000 では例えば

| サイズ | 本数 |
|---|---|
| 1.0mm×73mm | 21, 26 |
| 0.6mm×82.5mm | 22, 29, 36 |
| 1.0mm×53.5mm / 0.8mm×53.5mm | 30, 47, 50 |
| 1.0mm×40.0mm | 15, 24, 40 |
| 1.0mm×33.0mm | 16, 29, 46 |
| 1.0mm×63.0mm | 49 |

> **訂正（2026.09）**
> これ以前に「影響は最大 +0.016kg / 風袋・GW が変わるのは 3 通りだけ」と
> 報告したが **誤りだった**。チップボールの指定に無効な値を渡して測って
> しまい、外周 GAI が 0 になって HB の差が約 1/6 に縮んでいた。
> 正しくは上表のとおり。

### 設定 `hb_ta_legacy_divide` は廃止

① ② を選ぶ切替は不要になったため削除した。
ハードボードの高さを将来調整する場合は `HB_BAND_CLEARANCE_M`（A-1b）を使う。

## A-1b. 胴巻き HB の高さ -20mm → **採用しない（2026.09 確定）**

「積高ぴったりだとバンドを締めたときに割れるから低くしたい」という話を
実測と突き合わせた結果、**採用しないと判断**。

| 構成 | 積高 | 使用板 | 差 |
|---|---|---|---|
| 53.5 × 11本 | 596.9 | HB590 | **-6.9** |
| 53.5 × 10本 | 542.7 | HB530 | **-12.7** |

**差が一定でない。** 在庫サイズの直近下位を選んでいるだけで、
現場カットの精度を考えると「固定の締結代」という概念が成立しない。

### 追加の回答（2026.09）― **そもそも指定できない**

> 「もう一度重量測定する。**高さは指定 HB でない場合はランダム。答えようがない**」

ハードボードは 2 通りある。

| | 板 | 高さ |
|---|---|---|
| **固定物**（53.5mm × 10/11本） | `HB590*2000` / `HB530*2000` | 品番で決まる。**高さは計算に使わない**（マスタの固定値 × 2 枚） |
| **標準**（それ以外） | 在庫から現場でカット | **ランダム**。決まった寸法が無い |

標準 HB は**現場でカットするので高さが一定しない**。
つまり「積高より ◯mm 低い」という基準は**存在しない**。
`HB_BAND_CLEARANCE_M = 0`（補正しない）で確定。

> 重量は測り直すとのこと。単重はマスタ（`ハードボード`）から読むので、
> **マスタを更新すればアプリ側の変更なしで反映される**
> （更新日時を見て自動で読み直す。docs/04 §2.2）。

**移植での扱い** 受け皿だけ用意し、値は 0。

```python
HB_BAND_CLEARANCE_M = 0.0     # 現状 0。将来基準が決まればここだけ変える
HB_MIN_HEIGHT_M     = 0.05    # 補正後の下限。割る場合は補正しない

def get_hb_band_height(ta):    # VBA GetHBBandHeight
    h = ta - HB_BAND_CLEARANCE_M
    return ta if h < HB_MIN_HEIGHT_M else h
```

胴巻き HB の重量はこの関数を通す。
八角 HB（上下 2 枚）はマスタ固定値なので補正の影響を受けない。

## A-4. 積み高さクイック計算だけ 53.5mm が 43.5mm になっている → **53.5 に統一（2026.09）**

**場所**: `CommandButton13_Click`

```vba
ElseIf .CheckBox5 = True Then
  col = 43.5                      ' 他の全箇所は 53.5
...
ElseIf .OptionButton5 = True Or .OptionButton6 = True Then
  col = 43.5                      ' 同上
```

`SetCoilDimensions` / `GetHBCoilDimensions` / `GetSelectedCoilWidth` はいずれも 53.5。
フォームにも「2019.04.25 43.5mm削除 53.5mm追加」の赤字注記があり、
**差し替え時の修正漏れ** と判断した。

**移植での扱い** **53.5 に統一した。**（唯一、値を変えた箇所）
戻したい場合は `config/app.json` で指定できる。

```json
"quick_height_width_override": { "53.5": 43.5 }
```

### この機能は何をするものか

指定サイズ画面の **「積み高さ計算」** ボタン。
コイルの本数を聞いてきて、パレットに積んだときの高さの目安を返すだけのもの。
**画面に出るだけで、ラベルにも風袋計算の帳票にも一切出ない。**

10 本で試すと、こう違う。

| | ﾁｯﾌﾟ | 1 条分 | ﾊﾟﾚｯﾄ+分(繰上値) | そのまま |
|---|---|---|---|---|
| いまの移植（53.5） | 7.7 | **61.2** | 370 | 361.2 |
| 旧 VBA のまま（43.5） | 7.7 | **51.2** | 360 | 351.2 |

### 決定（2026.09）― **53.5 のまま**

- 計算に使う他のすべての箇所（`SetCoilDimensions` / `GetHBCoilDimensions` /
  `GetSelectedCoilWidth`）が 53.5 で、ここだけが 43.5 だった。
- フォームに「2019.04.25 43.5mm削除 53.5mm追加」の赤字注記が残っており、
  **差し替え時の直し漏れ**と読むのが自然。
- 仮にこの判断が違っていても、**帳票の数値は 1 つも変わらない**（参考表示のみ）。

旧値に戻したくなったら `config/app.json` の 1 行で戻せる。

## A-5. HB 行の計算式の `CoilH1` 依存 → **移植側では条件そのものが不要（2026.09）**

**場所**: `WriteSheetFormulas` と `WriteHBToSheet`

VBA では **風袋計算シートのセルへ書く**処理が 2 つに分かれていた。

| セル | 誰が書くか | 条件 |
|---|---|---|
| HB 行の**値**（B列） | `WriteSheetValues` | 無条件 |
| HB 行の**計算式**（C列） | `WriteHBToSheet` | **`If CoilH1 <> "" Then`** |

`WriteSheetFormulas` は C 列を i+1〜i+5、i+7〜i+12 に書くが、
**i+6（ハードボード）だけ書いていない**。そこは `WriteHBToSheet` の担当だった。

```vba
Cells(i + 5, 3) = ...   ' ポリシート
Cells(i + 7, 3) = ...   ' 樹脂パレット   ← i+6 が飛んでいる
```

そのため `CoilH1` が空で `CoilH2` 以降だけ入力した場合、
**HB の計算式の欄だけが空になる**（重量の値は入る）。

### 移植での扱い ― **条件を持たない**

> 「WriteHBToSheet は正直パイソン側では不要かもです。
> SetHBDisplayForm の機能と勘違いしてました」

そのとおりで、`WriteHBToSheet` は **Excel のセルへ書き込む**処理。
移植版は画面をデータから描くので、**セルへ書く処理そのものが無い**。

計算式は `mat.formulas["HBsiki"]` に必ず入っており、
`sheet_formulas()` が他の資材と同じように返す。
**出す・出さないの条件を持つ理由が無い**ため、条件ごと削除した。

| | 旧 VBA | 移植版 |
|---|---|---|
| HB の計算式 | `CoilH1` が空だと欠ける | **常に出る**（他の資材と同じ） |
| HB の重量・風袋・GW | 正しい | 変わらず正しい |

**数値には影響しない。** 表示欄だけの話。

> 経緯: 当初は VBA の挙動をそのまま再現し（`hb_formula_written`）、
> ご指示を受けて梱包ごとの判定に改めた。その後
> 「セルへ書く処理と表示の処理を取り違えていた」とのことで、
> 条件自体を外した。VBA 側の `WriteHBToSheet` は
> シート運用が続く限り必要なので、そちらはそのままでよい。

## A-6. 入力を変えて「計算」せずに刷ると値が混ざる 【安全】

**場所**: `CommandButton1`（重量反映）と `CommandButton16`（計算）

ラベル台紙に書かれる項目は、**書かれるタイミングが 2 つに分かれている**。

| 台紙の項目 | 書くところ |
|---|---|
| **検査番号・重量・型番** | `重量反映`（`ExecuteWrite` / `チェック入力`） |
| **本数・高さ・NW・GW** | **`計算`**（`ラベル転記OP` / `ラベル転記CK`） |

そのため次の順で操作すると、**1 枚のラベルに別々のコイルの値が混ざる**。

```
1. 検番 Z987654 / 重量 22.0 / 本数 11  → 反映 → 計算 → （正しい）
2. 検番 Z111111 / 重量 33.0 / 本数 20  → 反映だけして印刷
   → 検番 Z111111・重量 33.0（新しい）
     本数 11・高さ 910.0・NW 242.0・GW 279.0（**前のコイルのまま**）
```

**VBA も同じ挙動**（シートは「計算」でしか書き換わらない）。
現場では「必ず計算を押す」運用で回っていたと思われる。

**移植での扱い**
**値は VBA どおり、一切変えていない。**
そのうえで、計算に使った入力（サイズ・チップボール・検番・重量・本数）を控えておき、
**現在の入力と食い違っていたら印刷画面の先頭で知らせる**。

出荷ラベルなので、黙って古い値を刷るのは避けたい一方、
値を勝手に作り替えるのも避けたい ―― という判断。
「計算」を押し直せば警告は消え、正しい値になる。

### 決定（2026.09）― **印刷そのものを止める**

> 「食い違っている間は印刷ボタン自体を止めたい」

| 止め方 | 内容 |
|---|---|
| 印刷ボタン | **無効**（「印刷（停止中）」と表示し、理由をツールチップに） |
| 台紙一覧の印刷リンク | **出さない**（「印刷（停止中）」の文字だけ） |
| **ブラウザーの印刷（Ctrl+P・メニュー）** | `@media print` でシートを出さず、**理由だけを紙に出す** |

ボタンを消すだけでは Ctrl+P で刷れてしまうため、
**印刷出力そのもの**を止めている（実測: 止めている間は PDF が
ラベル 2 ページ → 理由 1 ページになる）。

「計算」を押し直せば元どおり印刷できる。**計算結果は変えていない。**

## B-2. 検査番号の 3 文字目が検査されていなかった → **塞いだ（2026.09）**

```vba
If Not IsNumeric(Mid(ken, 2, 1)) Then
    MsgBox msg & "6桁目にアルファベットが入力されています"
```

### メッセージは間違っていなかった（2026.09 訂正）

当初これを「メッセージと判定位置が食い違っている」と書いたが、**誤りだった。**
メッセージは **右から数えた桁** を指していて、全部そろっている。

| 検査している位置（左から） | メッセージ | 右から数えると |
|---|---|---|
| `Mid(ken, 2, 1)` | 「**6桁目**にアルファベット」 | 7-2+1 = **6** ✓ |
| `Mid(ken, 7, 1)` | 「**1桁目**にアルファベット」 | 7-7+1 = **1** ✓ |
| `Mid(ken, 4, 4)` | 「**1〜4桁目**にアルファベット」 | 4〜7 → 右から **1〜4** ✓ |
| `Mid(ken, 1, 1)` | 「**7桁目**に数字」 | 7-1+1 = **7** ✓ |

7 桁の番号を右から数えるのは自然な読み方で、**文言を直す必要はない。**

### 本当の問題 ― **3 文字目が一度も検査されない**

検査しているのは 1 / 2 / 4〜7 文字目だけ。**3 文字目が抜けている。**

```
W111111   OK  ← 正しい
W1A1111   OK  ← ★3文字目が英字でも通ってしまう
WAA1111   NG  ← 2文字目で弾かれる（3文字目は見ていない）
```

`W1A1111` のような検番が**そのままラベルとバーコードに載る**。

### 決定（2026.09）― **塞ぐ**

3 文字目も数字であることを検査するようにした。
メッセージは既存と同じ数え方（右から）で「**5桁目**にアルファベットが
入力されています」。

**判定は一番最後に置いている。**
先に置くと、2 文字目と 3 文字目の両方が不正な入力のメッセージが
変わってしまう。最後なら

- これまで弾かれていた入力の文言は **1 つも変わらない**
- これまで通り抜けていたものだけが **新しく弾かれる**

| 入力 | 変更前 | 変更後 |
|---|---|---|
| `W111111` | OK | OK |
| `W1A1111` | **OK（通っていた）** | **NG「5桁目にアルファベット」** |
| `WA11111` | NG「6桁目…」 | NG「6桁目…」（変わらず） |
| `WAA1111` | NG「6桁目…」 | NG「6桁目…」（変わらず） |
| `W11A111` | NG「1～4桁目…」 | NG「1～4桁目…」（変わらず） |
| `1111111` | NG「7桁目に数字」 | NG「7桁目に数字」（変わらず） |

## B-5. チップボールのボタン名と実際に使う径が一致しない

| ボタン | 実際の外径 | 半径 | 外周 |
|---|---|---|---|
| TIP1000 | 1100 | 550 | 1100π/1000 |
| TIP950 | 1000 | 500 | 1000π/1000 |
| TIP820 | 900 | 450 | 900π/1000 |

旧版のコメントに「コイル直径を1100とする(パレットサイズと同等)」とあり、

| ボタン | 資材マスタの名前 | 計算に使う外径 | 半径 |

| TIP820 | `チップボール820ф` | 900 | 450 |

つまり **ボタン名 = チップボールの品番（シートの径）**、

別のものを指していると考えれば矛盾しない。

長さ計算（外周 `直径 × π`）に使うので、**チップボールの径ではなく

> 「合っている」

**ボタン名＝チップボールの品番、計算の外径＝梱包の外形**（一段大きい）。
別のものを指しているので矛盾しない。現行どおり。

## C-5. `Cells(dataRow, 2)` の表記ゆれ → **統一した（2026.09 決定）**

> **これはラベル用紙の話ではない。**
> VBA では 7 サイズ × 丈1/丈2 = **14 枚の Excel シート**があり、
> そのシートの `B3`（一部は `B92`）セルに「サイズ名の文字」が直接打ち込んである。
> ここで言う「台紙」は **その Excel シート**のことで、
> 実際に刷るラベル用紙は **全サイズ共通の 1 種類**（下記 E-6）。

実シートの `B3` は `1.0mm×53.5mm 　 丈1`（全角スペースの後に**半角スペースが1つ多い**）だが、
`BuildSheetName` が作るシート名は `1.0mm×53.5mm 　丈1`。
この値は印刷ヘッダーの「ｺｲﾙｻｲｽﾞ：」に出る。

### 回答（2026.09）― **統一してよい**

> 一度シートの名前だけでいろいろ設定してしまって当時のシート名に引っ張られています。
> 今更変えるとどこに影響が出るのかわからないのでそのままなだけです。
> つまりこのツールでは判別できれば統一してくれれば良いです。

Excel 側はシート名が各種設定の基準になってしまっていて直せないが、
**このツールはシート名に一切依存していない**（サイズの判別は `obIdx` で行う）。
そこで、**見える文字だけを統一した**。

### 揃えたもの

| | VBA（当時のシート名のまま） | このツール |
|---|---|---|
| 小数点が無い | `1.0mm×73mm` | `1.0mm×73.0mm` |
| 半角スペースが 1 個多い | `1.0mm×53.5mm 　 丈1` | `1.0mm×53.5mm 　丈1` |
| 他の 5 サイズ | （もともと揃っている） | 変化なし |

結果、**14 件すべてが `厚みmm×巾mm 　丈N` の 1 つの形**になった。

### 実装

`normalize_size_name()`（`app/services/size_master.py`）。
やることは **「整数だった値に `.0` を足す」だけ**で、桁を削ったり丸めたりはしない
（将来 `1.25mm` が来ても `1.25mm` のまま）。
サイズを追加しても自動で揃う。

### 計算への影響 ― **無い**

巾の取り出し（VBA `ExtractWidthFromName`）は `Val()` 経由なので、
`73mm` でも `73.0mm` でも同じ `73.0` になる。
`test_width_is_unchanged_by_the_rename` で 14 件すべてを突き合わせている。

VBA の元の文字列は `_BUILTIN` と `data/size_master.json` の `baseName`、
およびテストの `VBA_TABLE` に**そのまま残してある**（記録を失わないため）。

### 元に戻したくなったら

`data/size_master.json` の該当サイズに 1 行足せば、そのサイズだけ実シートの
字間に戻せる（仕組みは残してある）。

```json
"sizeCellLabel": { "5": "1.0mm×53.5mm 　 丈1", "6": "1.0mm×53.5mm 　 丈2" }
```
