# DB 運用・長時間起動・同時実行の確認事項

現場からの指摘（Access→SQLite の置き換え／長時間放置／複数 PC の同時書込）に対する
**現状の設計・実測値・残る確認事項**をまとめる。

---

## 0. 前提 ― 現在の設計に「Access → SQLite の置き換え」は含まれていない

まずここを揃えておきたい。現在の移植版は 2 つの DB を**役割で分けて**使っている。

| | 何を入れているか | 形式 | 置き場所 | 読み書き | 共有 |
|---|---|---|---|---|---|
| **資材マスタ** | 梱包資材の単位質量・係数 | **Access `.accdb`** | 共有フォルダー（`aim_ref_path`） | **読取専用** | 全 PC が読む |
| **アプリ状態** | 台紙のセル・風袋計算結果・画面の入力状態 | **SQLite `.sqlite3`** | `%LOCALAPPDATA%`（**PC ごとにローカル**） | 読み書き | **共有しない** |

つまり、

- **Access は今もマスタのまま**で、SQLite へ置き換えてはいない。読むだけで書き込まない。
- **SQLite は VBA で「シート」が担っていた状態の置き場**として新設したもので、
  Access から移したデータではない。1 台 1 利用者のローカル状態。

この結果、ご指摘のうち次のものは **現時点では発生しない**。

| ご指摘 | 現状 |
|---|---|
| 複数 PC からの共有アクセス（SQLite） | 発生しない。SQLite はローカル領域にあり共有しない |
| 書き込み競合 / 同時更新によるデータ消失 | 発生しない。書き込むのは自分の PC の自分だけ |
| 共有フォルダ上の SQLite 運用 | 該当しない。共有フォルダーに SQLite は置いていない |
| 読み取り中に別 PC が書き込む | 資材マスタ（Access）は全員読むだけなので競合しない |

**ただし「今後 Access を SQLite へ置き換える」なら、いずれも直ちに効いてくる。**
その場合の判断材料を §1 と §3 に書く。

## 1. Access → SQLite へ置き換える場合の確認事項

### 1.1 接続方式の変更

| | 現在（Access） | SQLite にした場合 |
|---|---|---|
| 経路 | Python → `cscript.exe` → VBScript → ADODB → ACE OLE DB | Python → `sqlite3`（標準ライブラリ） |
| 外部依存 | **ACE ランタイムが必要** | **不要** |
| 起動コスト | プロセス起動のぶん 1 回あたり数百 ms | ほぼゼロ |
| 失敗しやすい点 | ACE 未導入 / 32bit・64bit 不一致 / ネットワーク断 | ファイルの権限・ロック |

**置き換えの利点は小さくない。** ACE への依存と `cscript` 経由の往復がなくなり、
「ライン PC に ACE が入っているか」という前提そのものが消える。
移植の構造上、差し替えるのは `app/repositories/` の 1 ファイルだけで、
業務ロジック（`app/services/`）には手を入れない。

### 1.2 SQL 方言・データ型の差

本システムが Access に対して実行しているのは **`SELECT * FROM [資材重量]` の 1 種類だけ**
（書込・DDL・結合・集計なし）。そのため方言の差はほぼ問題にならない。

| 論点 | Access(ACE) | SQLite | 影響 |
|---|---|---|---|
| 識別子の囲み | `[資材重量]` | `[...]` も `"..."` も可 | なし |
| 日本語のテーブル名・列名 | 可 | 可（UTF-8） | なし |
| `ф`（キリル文字）を含む資材名 | UTF-16 で保持 | UTF-8 | **要確認**。移行時の文字化けに注意 |
| 数値型 | 通貨型は固定小数（10,000倍の整数） | `REAL` は倍精度浮動小数 | **要確認**。下記 |
| 型の厳密さ | 列の型が固定 | 動的型（列に文字列も数値も入る） | 影響小。下記 |
| NULL | あり | あり | なし |

**単位質量の型が要確認。** `単位質量` が Access の **通貨型（Currency）** の場合、
Access 側は固定小数で保持している。SQLite の `REAL` へそのまま移すと
二進浮動小数になり、末尾の桁で差が出ることがある。
資材単重は 9 資材ぶんが積み上がって風袋・GW になるため、
**移行するなら `TEXT` で保持するか `INTEGER`（1/10000 倍）で持つ**のが安全。

移植側は `val()`（VBA の `Val()` 相当）で文字列・数値のどちらでも受けられるようにしてあるため、
**`TEXT` で持たせても現行の計算結果は変わらない。**

### 1.3 Access 特有の処理の棚卸し

VBA には ADO の汎用ライブラリ（`fldAccdb` / `AddAccdb` / `adoSQL` / `XlsToAccdb` /
`ADOX.Catalog` によるテーブル作成など）が入っていたが、
**本システムからはいずれも呼ばれていない**（解析書 §4.1、移植対応表 §8）。

本システムが Access に依存しているのは次の 3 点だけで、置き換えの影響範囲は狭い。

| 依存 | 置き換え後 |
|---|---|
| 接続文字列 `Provider=Microsoft.ACE.OLEDB.12.0` | 不要 |
| カーソル `adOpenStatic` + `adLockReadOnly` | 不要（読取のみ） |
| `GetUnitMassAndCoefficient` の**資材名の完全一致**（`ф` を含む） | **そのまま維持が必要** |

### 1.4 複数 PC からの共有アクセス・書き込み競合

→ **§3 にまとめる。ここが置き換えの最大の判断点。**

## 2. ツールを起動したまま長時間放置した場合

ご指摘を受けて実測し、**2 件の実害を確認して修正した。**

### 2.1 DB 接続を保持し続ける設計になっていないか → **なっていた。修正済み**

**修正前の問題。** `ThreadingHTTPServer` はリクエストごとにスレッドを作る。
状態ストアが接続を**スレッドごと**に持っていたため、
リクエストのたびに SQLite 接続とファイルハンドルが増え、
スレッドが GC されるまで閉じられなかった。

実測（`/api/state` を連続実行）:

| | 修正前 | 修正後 |
|---|---|---|
| 500 リクエスト後の SQLite 接続数 | **最大 37**（GC 任せで increase/decrease） | **1（固定）** |
| 500 リクエスト後のファイルハンドル数 | **最大 92** | **6（固定）** |

**修正後の方針。**

- 接続は**プロセス全体で 1 本**。全操作を 1 つのロックで直列化する。
  1 台 1 利用者・書込量が小さいため、直列化による体感差はない。
- **無操作が `db_idle_close_sec`（既定 120 秒）続いたら接続を自動的に閉じる。**
  放置中は DB ファイルのハンドルを掴まないので、バックアップ・ウイルス対策・
  フォルダー削除を邪魔しない。次の操作で自動的に開き直す（利用者には見えない）。
- `/diag` 画面で「開いている / 閉じている（アイドル解放）」と無操作秒数を確認できる。

### 2.2 古いデータを保持したままにならないか → **なっていた。修正済み**

**修正前の問題。** 資材マスタを初回に 1 度読んだきりキャッシュし続けていた。
朝ツールを起動したまま昼にマスタが更新されても、**古い単重で計算し続けていた**
（`/diag` の手動リロードを押さない限り気付けない）。

**修正後の方針。**

- 取得元ファイルの**更新日時とサイズ**を記録し、変わっていれば**自動で読み直す**。
- `material_refresh_sec`（既定 300 秒）の間は `stat` を省略し、
  共有フォルダーへの問い合わせを増やしすぎない。`0` で毎回チェック。
- **取得元へ一時的に到達できない場合は、直前に読んだ内容で業務を継続する**
  （ネットワーク瞬断でライン作業を止めないため）。
  このとき `/diag` に「取得元に到達できません／直前の内容で継続中」と表示する。

### 2.3 セッション切れ・ブラウザ放置後の再操作

**本アプリにセッションの概念はない**（ログインもクッキーもない）。
状態は SQLite に持続するため、**ブラウザを何時間放置しても「セッション切れ」は起きない。**
放置後に操作すれば、そのまま続きから使える。

ブラウザ側は 15 秒ごとに `/api/health` を確認し、
バックエンドが落ちていれば画面右上に「接続なし ― 再読込してください」と出す。
**「画面が開いている」ことと「バックエンドが生きている」ことを分けて扱う**設計
（基盤仕様書 2.9・監視レベル 1）。

> **D-3（回答あり 2026.09）**: 「複数作業者が使う。ただし同じ PC で同時かというと…」
>
> **PC が違えば互いに影響しない。** 状態はその PC の
> `%LOCALAPPDATA%` に持つので、ライン PC ごとに完全に独立している。
> 作業者が変わっても、その PC の続きから使える（VBA と同じ感覚）。
>
> 共有されるのは **同じ PC で 2 つのタブを開いた場合だけ**。
> 片方で選んだサイズが他方にも反映される。
> VBA は UserForm が 1 つだけだったので同じ状況は起きなかった。
> **これは「1 台につき 1 画面」という現行どおりの運用なら起きない。**
> もし 1 台で 2 画面を並べて別々の検番を扱いたい場合は、
> タブごとに状態を分ける改修が必要になるので、そのときに言ってほしい。

### 2.4 メモリ・ファイルハンドル・ロックの問題

| 項目 | 現状 |
|---|---|
| SQLite 接続 | 1 本固定。無操作で自動解放（§2.1） |
| ファイルハンドル | 実測 6 で頭打ち。放置中はさらに 1 つ減る |
| `-wal` / `-shm` ファイル | **作らない**（`journal_mode=DELETE`）。DB ファイルは常に 1 つ |
| メモリ | 状態は SQLite に置き、プロセス内に溜めるのは資材マスタ 1 表のみ（十数行） |
| スレッド | リクエストスレッドは処理後に終了。常駐は アイドル監視 1 本のみ |
| ログ | `RotatingFileHandler`（2MB × 5 世代）。無制限に増えない |

### 2.5 日付変更をまたいだ場合

帳票の「`yyyy.mm.dd` 印刷」は**画面を描くたびに取得**している
（`pages.py` の `datetime.date.today()`）。起動時に固定していないため、
**日付をまたいでも翌日の日付が正しく出る。**

`updated_at` は SQLite 側で `datetime('now','localtime')` を使っており、こちらも都度評価。

### 2.6 マスタ更新後の挙動

§2.2 のとおり自動追従する。
なお**すでに計算・印刷した結果は、更新後のマスタで自動的に再計算されない**
（VBA も同じ。再計算はボタンを押したときだけ）。

## 3. 複数 PC・複数ユーザーが同時に DB へ書き込む場合

### 3.1 現状は発生しない（D-4: 将来はあり得るとの回答）

SQLite（状態）はローカル領域にあり共有していない。
共有しているのは資材マスタだが**全 PC が読むだけ**なので、
書込競合も `database is locked` も起きない。

**「読むだけ」は自動テストで固定してある**
（`tests/test_db_runtime.py` の `TestSharedMasterIsReadOnly`）。

| 確かめていること |
|---|
| 共有マスタを読んでも**中身も更新時刻も変わらない** |
| `-wal` / `-shm` / `-journal` を**残さない**（共有フォルダーで他 PC の邪魔をしない） |
| 共有側が**読取専用属性**で配られていても読める |
| 別プロセスが同時に読んでいても読める |
| 状態 DB は端末ごとで、共有マスタとは**別のファイル**である |

書き込みが 1 箇所でも混ざった瞬間にロックの問題が始まるので、
ここは「読むだけ」を崩さないことが要になる。

> **D-4 への回答（2026.09）: 複数 PC から同じ DB へ書き込む要件は「あり得る」。**
>
> その時点で必要になるのは **DB の置き場所の判断**であって、
> アプリ側の作り直しではない。§3.5 の選択肢のうち **B（1 台に集約）** を推す。
> Web アプリなので、バックエンドを 1 台で動かして各 PC はブラウザーで使えば、
> DB はそのサーバーのローカルディスクに置ける ―― 共有ファイル上の
> SQLite が抱える問題（ロック不信・WAL 不可・切断時の破損）が丸ごと消える。
>
> **共有フォルダーに SQLite を置いて複数 PC から書く構成は避けること**（§3.5）。

### 3.2 SQLite のロック挙動（置き換えを検討する場合の前提）

SQLite は**書込時にデータベース全体をロックする**（行ロックではない）。

- 読取同士 … 同時に可能
- 読取と書込 … 書込中は読取を待たせる（`journal_mode=DELETE` の場合）
- 書込同士 … **必ず直列**。待てなければ `database is locked`

### 3.3 実装しているトランザクション・待ち・リトライ

置き換えに備えて、状態ストアには次を入れてある。

| 対策 | 値 | 目的 |
|---|---|---|
| `busy_timeout` | 15,000 ms（`db_busy_timeout_ms`） | 他プロセスのロック解放を待つ |
| 明示コミット | `isolation_level="DEFERRED"` + 操作ごとに `commit()` | 中途半端な書込を残さない |
| リトライ | `database is locked` / `busy` のとき **3 回**（0.4→0.8→1.2 秒） | 一時的なロックを乗り切る |
| 接続の作り直し | ロック失敗時は接続を捨てて開き直す | 壊れた接続を引きずらない |
| 複数書込の一括化 | `executemany` + 1 コミット | ロック保持時間を短くする |

**ローカルファイルでの実測**（4 プロセス × 40 書込 = 160 件、同時実行）:

```
プロセス0: 成功=40 失敗=0
プロセス1: 成功=40 失敗=0
プロセス2: 成功=40 失敗=0
プロセス3: 成功=40 失敗=0
DB内の件数 = 160 / 期待 160     ← 消失なし
```

**ただしこれは「ローカルディスク上」の結果である。**
共有フォルダー（SMB）上では同じ保証がない。理由は §3.5。

### 3.4 読み取り中に別 PC が書き込む場合

SQLite はトランザクション単位で一貫性を保つため、
**読取の途中で他の書込が混ざって半端な内容が見えることはない**（ローカルでは）。
本アプリの読取は 1 クエリで完結するため、読み取り中の書込による不整合は発生しない。

### 3.5 共有フォルダー上の SQLite 運用の妥当性 ― **推奨しない**

**結論: 共有フォルダーに SQLite を置いて複数 PC から書き込む構成は避けるべき。**

理由:

1. **ファイルロックが信頼できない。** SQLite のロックは OS のファイルロックに依存する。
   SMB / NFS ではロックの実装差・キャッシュ・切断時の取り残しがあり、
   SQLite 公式も network filesystem での同時書込を**破損の原因として警告**している。
2. **WAL が使えない。** WAL は共有メモリ（`-shm`）を使うため、
   ネットワーク上のファイルシステムでは動作保証がない。
   → 本アプリが `journal_mode=DELETE` を選んでいるのはこのため。
3. **切断時の被害が大きい。** 書込中にネットワークが切れると、
   ロックが残る・ジャーナルが中途半端に残る、といった形で
   **DB 全体が壊れうる**（1 レコードの失敗では済まない）。
4. **遅い。** 1 回の書込でファイルの複数箇所に触れるため、往復が増える。

検出のため、**状態 DB が UNC・ネットワークドライブ上にあると警告ログを出す**
仕組みを入れてある（`is_network_path`）。`/diag` にも「ローカル領域 / ネットワーク上」を表示する。

#### 複数 PC で使いたい場合の選択肢

| 案 | 内容 | 向き・不向き |
|---|---|---|
| **A. 現状維持（推奨）** | マスタは共有の読取専用、状態は各 PC ローカル | 今の運用に一致。競合が原理的に起きない |
| **B. Web アプリを 1 台に集約（推奨）** | サーバー 1 台でバックエンドを動かし、各 PC はブラウザーで使う。DB は**そのサーバーのローカルディスク** | 共有ファイルの問題が消える。**Web 化した利点がそのまま効く** |
| C. サーバー DB へ | PostgreSQL / SQL Server 等 | 同時書込が本当に必要ならこれ。運用負荷は増える |
| D. 共有フォルダーに SQLite | — | **非推奨**（上記の理由） |

> **B を採る場合の注意（D-3 と同根）**: 現在 `form_state` は
> **利用者を区別しない 1 件のキー**として保存している。
> 1 台に集約すると、**複数の作業者が同じ入力状態を奪い合う**ことになる。
> 集約するなら、まず「利用者ごと（またはライン・端末ごと）に状態を分ける」改修が必要。
> 計算ロジックには影響せず、`Workflow.load_state/save_state` のキーを分けるだけで済む。

| **D-8** | 取得元に到達できないとき、直前の内容で継続してよいか | B | **継続する、ただし画面に出す（2026.09 確定）**。ネットワーク瞬断でラインを止めないため継続し、全画面のヘッダーの取得元バッジを赤くして「（古い内容）」と出す。一度も読めていなければ VBA と同じく「資材重量なし」で止まる |
| **D-9** | ツールは何時間くらい起動したままにするか | C | **確認不要（2026.09）**。何時間でも動く作りになっている（接続は都度開閉、状態は SQLite に永続化、メモリに溜め込むものが無い）。長時間でも困らないので、実際の時間を聞く必要が無くなった |

## 6. DB まわりの点検（2026.09）

依頼の観点を 1 つずつ、**実際に動かして**確かめた。
固定したものは `tests/test_db_concurrency.py`（20 件）。

### 問題なかったもの

| 観点 | 確かめ方 | 結果 |
|---|---|---|
| SQL 方言 | 発行している SQL を全て確認 | マスタは `SELECT * FROM [資材重量]` のみ。WHERE も関数も結合も無い。`IIf` `Nz` `Format` `DLookup` `#日付#` `LIKE '*'` など Access 方言は**不使用** |
| データ型の差 | TEXT `0.5` `.5` `0.50` ` 0.5 ` / REAL `0.5` を読み比べ | すべて `Val()` を通って **0.5 に一致**。Access が通貨型でも倍精度でも同じ |
| 資材が無い場合 | 存在しない資材名で計算 | VBA と同じく **0kg で静かに続行** |
| 多スレッド同時書込 | 8 スレッド × 40 回 | 例外なし・値の取りこぼしなし（接続 1 本をロックで直列化） |
| database is locked | 別プロセスが 1 秒ロックを保持 | 待って成功（busy_timeout + 再試行）。**双方の書込が残る** |
| 読み取り中に別 PC が書込 | 書込スレッドと並行して 120 回読む | 例外なし |
| WAL のマスタ | 他システムが WAL で書いた DB | 読めた |
| マスタ更新の検知 | 起動したまま差し替え | 読み直す。`material_refresh_sec` の間は古いままで、過ぎたら追いつく |
| 長時間放置 | アイドル解放 | 接続を閉じ、**ファイルハンドルが 0 になる**。次の操作で開き直す |
| ブラウザ放置・戻る | 実ブラウザで確認 | 使用権は持ち主のまま。操作できなくならない |
| 日付変更 | 日付依存処理を全検索 | `updated_at` と表示のみ。**計算・判定に日付は一切入らない** |
| 共有フォルダ上の SQLite | 設定項目を確認 | 状態DB のパスは**設定できない**（常に `%LOCALAPPDATA%`）。共有に置けないので複数 PC から書く事故が起きない。共有側のマスタは **読取専用**（`mode=ro`） |

### 見つかって直したもの

**① 失敗した操作の書込が、後から確定していた**

`_run()` はロック以外の失敗で **rollback せずに再送出**していた。
そのため途中まで書いた内容が接続に残り、
**次の無関係な書込の commit で一緒に確定**していた。

```
操作1: 'half' を書く → 次の文で失敗 → 例外
操作2: 無関係な 'other' を書く
結果:  DB に half と other の両方が残る   ← 直す前
       DB に other だけが残る             ← 直した後
```

→ どんな失敗でも rollback する。**1 回の呼び出し = 1 トランザクション**。

**② 時計がずれると画面を奪われた**

経過時間を `time.time()`（壁時計）で測っていたため、
NTP 補正や手動の時刻変更で**1 時間進んだだけ**で
「誰も使っていない」と誤判定し、作業中の画面を別のタブに渡していた。

→ 経過時間は `time.monotonic()`（進むだけの時計）で測る。
画面ガード・アイドル解放・マスタ鮮度の 3 か所。表示は壁時計のまま。

**③ 放置で期限切れになっただけでも「使用中ではなくなりました」と出た**

生存通知が「他に取られた」と「誰も使っていない」を区別していなかった。

→ `heldByOther` を返し、誰も居なければ**黙って取り直す**。

**④ 裏に回したタブの心拍が間引かれ、次に開いたタブに画面を奪われた（2026.09.25）**

別ツールで「ブラウザーが裏のタブのタイマーを間引き、心拍が途切れてセッションが
誤って終了した」事故があり、本ツールも確かめた。

- **サーバーのプロセスは心拍では止まらない**（自動で止める仕組みを持たない。
  止めるのは stop.bat / 終了の操作だけ）。作業状態も SQLite に残る。
- ただし **入力画面の使用権** は心拍で決まる。Chrome / Edge は裏のタブの
  タイマーを間引く（5 分ほど裏にあると 1 分に 1 回まで。眠ったタブ・
  PC のスリープでは止まる）ため、20 秒途切れて「空き」と判定され、
  そこで開いたタブ（Start.vbs からの起動でも開く）が使用権を取っていた。
  戻った作業中の画面は「この画面は使用中ではなくなりました」になる。
  **旧コードで再現した**（通し確認で「奪われた」）。

→ 対策（`services/screen_guard.py` / `static/js/app.js`）

| 仕組み | 内容 |
|---|---|
| 裏に回るときの知らせ | `visibilitychange`(hidden) と `freeze` で `/api/screen/state` へ `sendBeacon`（凍結・閉じる途中でも届く） |
| 空き判定の抑制 | 裏に回ると知らせた画面は **12 時間** 心拍なしでも空きにしない（表なら従来どおり 20 秒）。心拍にも表裏を載せ、知らせが届かなくても分かる |
| 表への復帰の検知 | `visibilitychange`(visible)・`resume`・`pageshow`(bfcache)・`focus`・`online` で**タイマーを待たず**に生存を知らせ、接続表示も更新 |
| スリープ復帰の検知 | 表のまま時計が 30 秒以上飛んだらスリープ（凍結）から戻ったとみなし、すぐ知らせる。ログに「スリープ・凍結から戻りました」 |
| 次に開いたタブ | 断る画面に「その画面はいま裏に回っています（何時から）」と出す。本当に見つからないときは「この画面で使う」で移せる |

ブラウザーが落ちた場合（表のまま応答が消えた）は、従来どおり 20 秒で次に譲る。
確かめ方: `tests/test_screen_guard.py` の `BackgroundTabTest`（時計を差し替えて何時間も進める）と、
`tools/smoke_all.py` の「裏に回ったタブ」（実ブラウザーで心拍を 22 秒止め、次のタブが断られること）。

### 残しておく判断

- **複数 PC から同じ状態DB へ書く運用はしない。** 状態は端末ごとに独立で、
  共有するのは読み取り専用のマスタだけ。将来書き込みが要るなら §5 の設計。
- **WAL は使わない。** ネットワーク FS で動作保証が無く、`-wal`/`-shm` が増える。
  書込量が小さく利点が無い。

## 7. マスタを直すと印刷に届くか（2026.09 確認）

「マスタを直したのに古い内容で刷られた」は、コイルに違う型番の
ラベルが貼られるということなので、**取りこぼしを許さない**扱いにした。

### 確認したこと（`tests/test_master_admin.py`）

画面から直した場合だけでなく、**このアプリを通さずに別の PC が
直した場合**も確かめている。

| 確かめたこと | 結果 |
|---|---|
| 別プロセスが型番を直す → **バーコードの中身**と文字の両方が変わる | ○ |
| 14 枚すべてに効く（1 枚も取り残さない） | ○ |
| 続けて 4 回直しても毎回反映される | ○ |
| **同じ長さの値**で直しても気付く（ファイルサイズが変わらない） | ○ |
| 資材重量を外から直す → 計算・ラベル・風袋帳票に効く | ○ |

バーコードは見た目ではなく **SVG の実体（`aria-label`）** で確かめている。

### そのために直した 2 か所

**① ラベル台紙は開くたびに読み直す**

以前は 5 秒間キャッシュしていたため、その間に別の PC で直された内容が
反映されなかった。読むのは 14 行の小さな表で、開くのも印刷のときだけ
なので、**間隔を置かず必ず読み直す**ことにした。

**② 「計算」を押した瞬間は必ずマスタを確かめる**

資材重量は鮮度チェックの間隔（既定 300 秒）に守られており、
外から直した単重が最大 5 分間反映されなかった。

```
直す前の GW 274.0
外から テスラピン を 99.0 に変更
重量計算_DB を押す → GW 670.0   （帳票・ラベルにも同じ値）
```

`load(check_now=True)` で間隔を飛ばす。確かめるのは `stat` 1 回で、
変わっていなければ読み直さないため、共有フォルダーへの負荷は増えない。
